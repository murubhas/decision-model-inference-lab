Optimizing Inference with a Decision Model

Generate with generative models. Decide with decision models.

A measured guardrail case study using Jev, Bedrock, and hybrid routing in a Quarkus A2A agent. An LLM-based guardrail evaluation turns bounded semantic questions into a generative inference call — this experiment routes each check to the model best suited to it and measures the difference.

The question: which semantic checks need a generative model — and which only need a decision?
Frame the subject first: this talk is about an architectural pattern — routing repeated bounded decisions to a decision model as an inference optimization. Jev is the decision model we tested; semantic guardrails are the realistic repeated-decision scenario. Our Quarkus A2A agent checks three boundaries — input, tool call, final output — and in the all-LLM control each boundary evaluation is a generative Bedrock call: tokens, latency, cost, and one more generated-output contract that can fail. This is an engineering experiment, not a product pitch: corpus, questions, action policy, and environment stayed fixed while five paths were measured. The headline comparison keeps the original LLM, Jev, and Hybrid paths; the two self-hosted Strands paths are in the appendix. All aggregate numbers come from 510 measured observations across three repetitions after one excluded warmup. Land the thesis: generate with generative models, decide with decision models.

Why a decision model?

Generating JSON token by token is a lot of machinery for a yes/no answer

A guardrail check has a bounded outcome. A generative judge still has to write it out one token at a time — and your code has to parse what it wrote.

Close with the caution: typed output removes that parser problem, not the possibility of a wrong answer. That distinction drives the whole experiment.

System One and Noul

Noul: a typed yes/no semantic question

Jev, the System One decision model this experiment measured, evaluates narrow, typed questions over TypeSafe's API. The simplest primitive, Noul, answers one question: how probable is it that this condition is true?

A typed yes/no semantic question

You state the condition and explicit true/false criteria over named state fields. Several independent questions batch into one request.

Returns probabilityTrue

One scalar per Noul question. No prose, no markdown fences, no generated JSON to repair.

Application code owns thresholds and actions

The model supplies judgment; Java policy maps probability to ALLOW / BLOCK / ESCALATE. Risk policy never lives inside a prompt.

No text generation, no prose parsing

It cannot write your recommendation or explain itself — and that is the point. It decides; it does not generate.

Request — state + one Noul question

{
  "model": "jev-latest",

Explain Noul without mystique: it is a typed yes/no semantic question. You send named state fields plus the condition and explicit true/false criteria; you get back one scalar, probabilityTrue. Walk the worked example left to right: the request carries the actual message, the response is 0.16, and Java code — not a prompt — turns that into an action. Stress the ownership split: models supply judgment, code owns thresholds and risk policy. The thresholds shown are deliberate bootstrap values used in shadow mode; corpus-derived thresholds come before any enforcement.

Where each path belongs

A routing rubric you can apply to your own checks

The decision is per check, not per provider. Match each guardrail question to the model whose strengths it measured.

Use Jev when

  • the answer space is predefined
  • typed output is required
  • a confidence value is useful to the policy
  • the check repeats frequently
  • application code owns thresholds and actions

Use an LLM when

  • reasoning is open-ended
  • relevance or grounding is nuanced
  • the output must explain or synthesize
  • several judgments depend on each other

Use Hybrid when

  • checks have different measured strengths
  • common bounded checks can avoid generation entirely
  • weak or uncertain checks can route to the LLM

Where Jev is not a candidate

Generation Summarization Exact arithmetic Authorization Schema validation Deterministic evidence lookup

Hard rules stay in deterministic code. Judgment goes to a model. Generation goes to a generative model. Never the other way around. The main routing result uses Jev; Appendix A6 repeats the same corpus with self-hosted Strands and shows why thresholds do not transfer automatically.

This is the transferable slide — the rubric works even if the audience never touches TypeSafe. Jev-shaped checks: predefined answer space, typed output, useful confidence, high repetition, code-owned thresholds. LLM-shaped checks: open-ended reasoning, nuanced relevance or grounding, anything that must explain or synthesize, or interdependent judgments. Hybrid earns its complexity only when checks have measurably different strengths — which is exactly what the pilot showed. Finish on the red strip: don't reach for Jev where deterministic code is the right answer — authorization, schema validation, arithmetic, evidence lookup. Probabilities are not policy.

Sequence detail: the check-specific Hybrid path

Java routes each check before either provider runs. A successful Jev call and a failed Jev call follow different paths.

Provider fallback selects who supplies an answer.

Policy ESCALATE is a later application decision.

Across three repetitions: 93 Jev calls and 66 generative calls in 93 successful Hybrid decisions · confidence fallback 3.23% · generative-call avoidance 29.03%

Use only for Q&A. Successful path: Jev evaluates the JEV_FIRST questions with projected state; the confidence policy marks each answer clear or uncertain; LLM_DIRECT questions and uncertain Jev questions form one LLM batch; clear Jev answers and LLM answers merge in original question order; the action policy then maps the final probabilities to ALLOW, BLOCK, or ESCALATE. If nothing needs the LLM, the Jev evaluation is used directly. The red branch leaves the Jev call before the confidence decision. Under FALLBACK_TO_LLM, the current default, all original questions go to one LLM evaluation that is returned directly, with nothing to merge. Under PROPAGATE_FAILURE, the Hybrid evaluation stops with the provider failure. Keep the two ideas apart: provider fallback chooses who answers; ESCALATE is an application decision made afterwards. The 3.23% figure counts confidence fallbacks only, not planned LLM_DIRECT routes.

Appendix A4 · backup, untimed

Shadow mode: measure decisions before they control traffic

The configured semantic path still runs inline. Shadow records its verdict but does not change the live agent flow.

Semantic path determines how the verdict is produced.

Enforcement mode determines whether the verdict controls traffic.

Shadow measures guardrail behavior. It does not protect traffic.

One configured path runs (deployed default HYBRID). The benchmark runner is what compares all three paths.

Inline and synchronous: live behavior is preserved, but guardrail latency and provider cost still apply.

Hybrid’s Jev-to-LLM fallback happens inside the semantic path, before Shadow or Enforce is considered.

Use only for Q&A. Two separate questions: Hybrid answers “who judges each check?” and Shadow answers “does that judgment control traffic?” In Shadow, every hook still runs the configured semantic path inline, records the observed action or the unrecovered failure, and then returns success or continues — input to the primary model, tool call to MCP, output to the client — even for BLOCK or ESCALATE. That gives counterfactual evidence for false-block analysis, threshold calibration, provider reliability, and check-by-check promotion. It is the right mode now because the labels are draft, the thresholds are bootstrap values, and the three-repetition run still exposed strict LLM output-contract failures. Be clear about the limits: Shadow is not a safety control, because unsafe traffic still continues, and it is not free or asynchronous, because the semantic calls still execute inline and add latency and provider cost. Runtime telemetry records tokens, not dollars; cost is estimated from tokens in the benchmark report. Deterministic checks such as the tool allowlist and empty-output rejection still stop traffic in both modes. In Enforce, BLOCK and ESCALATE stop execution with their guardrail error codes, and an unrecovered provider failure fails closed.

Appendix A7 · broader context, untimed

Does this request need generative inference?

Avoid unnecessary model calls, then choose the right model for the work that remains.

Cache and reuse

Reuse a valid result while the relevant input, context, and policy remain unchanged.

Batch what can wait

Group non-interactive scoring into batch jobs to use serving capacity efficiently.

Keep hard rules in code

Authorization, schema checks, limits, and arithmetic belong in deterministic code.

Use decision models for judgment

For bounded yes/no or classification checks, evaluate Jev or Strands Decider before using a generative judge.

Which calls in your agent need generated content, and which only need a decision?

This study measured decision-model routing for guardrails. Caching and offline batching are additional opportunities to evaluate.

Connect the experiment to the wider inference optimization problem. First ask whether a model call is needed. A valid cached result can avoid repeated inference, but its key and expiry must account for relevant state and policy changes. Exact rules belong in code. Offline batching still performs inference and can improve serving efficiency when the workload permits waiting. When semantic judgment is needed, a decision model can supply a bounded answer, while generative models remain useful for content creation and checks that require deeper reasoning. Decision models still perform inference and can use GPUs, as our Strands A10G deployment does. The measured evidence in this talk covers guardrail routing only. The lab does not implement or benchmark a result cache or offline batch serving.
